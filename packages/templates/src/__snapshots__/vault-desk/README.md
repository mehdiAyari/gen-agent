# vault-desk

Answers bank customers about their transfers

A Spring AI agent generated by [gen-agent](https://www.npmjs.com/package/gen-agent) (profile `production`):
Spring Boot 4.1.1, Spring AI 2.0.1, Java 21.

## Run

Docker Compose starts the agent with Postgres, Redis and Keycloak:

```bash
export MISTRAL_API_KEY=...   # never commit it
export BANK_API_TOKEN=...   # never commit it
OLLAMA_HOST=0.0.0.0 ollama serve &   # Ollama runs on this machine, reachable from the containers
ollama pull qwen2.5:3b
docker compose up --build
```

Every request needs a token. Sign in as the `demo` user of the Keycloak started by Compose (password `demo`):

```bash
TOKEN=$(curl -s localhost:8180/realms/agent/protocol/openid-connect/token \
  -d grant_type=password -d client_id=agent-client -d username=demo -d password=demo | jq -r .access_token)
curl -s localhost:8080/api/chat -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"message": "Hello"}'
```

Without Docker, Java 21 is enough to build: `./mvnw` downloads Maven (checked against its SHA-256).
Point the agent at your own services with environment variables:
`DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD` (Postgres),
`REDIS_URL`,
`OIDC_ISSUER_URI` (your identity provider: Keycloak, Auth0, Entra ID…),
then `./mvnw spring-boot:run`.

Send back the returned `conversationId` with the next message to continue the same conversation (the last
20 messages are kept in Postgres).
Conversations belong to the user of the token: another user gets 404 for them.
Every reply carries `"aiGenerated": true`, so clients can tell users they are talking to an AI (EU AI Act).

## Limits

- 30 requests per user and per minute.
- 100000 model tokens per user and per day, given back in full at the end of each day.

Beyond, the agent answers 429 with `Retry-After`. Change them under `agent.limits` in `application.yml`.

## Chat page

Open http://localhost:8080 to talk to the agent in a browser (sign in as `demo` / `demo` with Docker Compose).
The page is plain HTML, CSS and JavaScript in `src/main/resources/static`: change it as you like.
It signs users in with the authorization code flow and PKCE, through the public client `agent-client`
(`OIDC_CLIENT_ID`), and sends their token with each message: the agent keeps no session.

## Cache

The first answer of a conversation is kept in Redis for an hour (`agent.cache.ttl`): the same user asking the same
question again gets it without a call to the model. It is never shared between users, and an answer that used a tool is never kept: it depends on live data.

A question of the same meaning gets the same answer too: the questions are turned into vectors with
`mistral-embed` and kept in Postgres (pgvector, table `agent_semantic_cache`). Two questions of the same user
share their answer when their similarity is at least 0.95 (`agent.cache.semantic.threshold`, from 0
to 1). An answer holding personal data is never kept.

## Personal data

Emails, phone numbers, IBANs, card numbers (Luhn-checked) and French social security numbers never reach the model:
they are replaced by tokens such as `[EMAIL_1]` before each call, and put back in the answer and in the arguments of
the tools. The values behind the tokens stay in Redis for 30d (`agent.privacy.ttl`). Names and
addresses are not detected: keep them out of the system prompt, or mask them in your own code.

The logs mask the same values, in messages and in stack traces; each line carries the correlation id of its request.

A user erases everything the agent keeps about them (conversations, personal data, cache, limits) with
`DELETE /api/me`. Users with the `agent-admin` role erase another user with `DELETE /api/users/{userId}`, the subject
of their token (the `admin` / `admin` user of the Keycloak started by Compose).
Roles are read from the `realm_access.roles` claim (`OIDC_ROLES_CLAIM`).

Conversations unused for 30d are purged every hour (`agent.memory.retention`), with their personal data.

## Human control

Calls to `blockCard` wait for the approval of the user who asked: the reply lists them in
`approvals`, `GET /api/approvals` lists those still waiting, and `POST /api/approvals/{id}` with `{"approved": true}`
or `false` makes the call or not, tells the model and returns its next answer. A call nobody approves expires
(`approval.expiresAfter` in agent.yaml), and only the user who asked can decide. The chat page shows Approve and Deny buttons.

Users with the `agent-admin` role switch the agent or one of its tools off at once, for every instance:
`PUT /api/admin/switches/agent` or `PUT /api/admin/switches/tools/{name}` with `{"on": false}`;
`GET /api/admin/switches` shows what is on. Switched off, the agent answers 503; a tool tells the model it is
unavailable.

## Resilience and cost

A failed call to the model is retried twice with a growing delay (`spring.ai.retry`). After repeated
failures a circuit breaker opens for 30 seconds (`resilience4j.circuitbreaker`): requests stop waiting on a model that is
down. Meanwhile, and whenever a call fails, `qwen2.5:3b` (ollama) answers instead, through its own breaker.
When no model can answer, users get the fallback answer of `agent.fallback-answer`, never an error page.

Simple messages go to `mistral-small-latest`, the others to `mistral-medium-latest` (`agent.routing`):
long messages, code, several questions or a request to explain, compare or plan (in English or French) are complex.
The model of each call is in its trace.

Beyond 20 messages, the older ones of a conversation are summarized by the model (`mistral-small-latest`) and kept as one
message, so that a long conversation keeps its facts without sending them all again.

## Guardrails

A message that tries to take over the agent (ignore your instructions, show your system prompt, you are now…, fake
system or tool messages, in English or French, plainly or in base64) gets a refusal (`agent.guard.refusal`) and never
reaches the model. Tool results reach the model between `<tool-result>` tags, as data it must not obey; once a
result holds instructions, only the tools that read data (`transferStatus`) stay callable for the rest of the request.
These are heuristics: they make an attack harder, they do not rule it out. Never give the agent a tool whose misuse
you could not accept.

An answer that repeats the system prompt is replaced by the refusal, and API keys (OpenAI, AWS, GitHub…) are masked.

The model may call tools 8 times to answer one message (`spring.ai.tools.limits.max-total-tool-calls`);
beyond, the request stops with 422.

A request may take 60s at most (`agent.timeout`), model calls and tools included; beyond, it is stopped
and answered with 504.

## Observability

Health and metrics answer on port 8081 (`MANAGEMENT_PORT`), not on the public one: `/actuator/health`, `/actuator/prometheus`.
Traces and metrics of every conversation (model calls, tools, tokens) go to OpenTelemetry when `OTLP_ENABLED` is
true: Docker Compose sends them to Grafana, at http://localhost:3000.

## Test

```bash
./mvnw verify
```

The tests use a fake model: they never call mistral and cost nothing.
Docker must run: the tests start Postgres and Redis in containers (Testcontainers).

## Where to put your code

| Path | Owner |
| --- | --- |
| `src/main/resources/prompts/system.md` | yours: the system prompt |
| `src/main/java/com/example/vaultdesk/tool/` | yours: the logic of your Java tools |
| `src/main/java/com/example/vaultdesk/generated/` | gen-agent: overwritten on regeneration, do not edit |
| `pom.xml`, `application.yml` | shared: gen-agent will merge its changes with yours |
